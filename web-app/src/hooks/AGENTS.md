# hooks — Domain-Logic Hooks

## Purpose

Stateful React hooks that encapsulate cross-cutting domain logic — MIDI device management, verdict transport, and the step-by-step practice session. Each hook owns a complex concern that would otherwise bloat page components.

## Ownership

- `useMidi.ts` — Web MIDI API integration via the `webmidi` package. Manages device enumeration, enable/disable lifecycle, input selection, live note-on/note-off tracking, two event streams, and hot-plug (connect/disconnect) events. Returns `UseMidiReturn` (the interface consumed by `MidiPanel` and `ScorePage`).
- `useVerdict.ts` — Carries a finished performance to the Cadenza service and holds the verdicts: the seven RML ones **plus the top-level `correct` list** (the coverage fact — attacks played right and on time — surfaced as `verdict.correct: ScoreLocation[] | null`, `null` while idle/no payload, emptied together with `verdicts` on every new analyse or `reset()`). `toPerformance(events)` is a pure function, exported for testing, converting the MIDI stream into the payload the service validates. It contains no threshold and no verdict: the verdict is computed in Prolog, and the coverage too — this hook only moves numbers. Its `Verdict` carries the optional `locations` array exactly as the service sends it (see `../../AGENTS.md` Service contract); deciding what to do with them is `scoreMarks.ts`, not this transport. `API_URL` defaults to the deployed service `https://cadenza-etji.onrender.com`; `VITE_CADENZA_API` overrides it for local development.
- The deployed URL is the default on purpose. It is a public address, not a secret, so hiding it behind an env var only created a way to forget it — and a forgotten env var points the app at the author's own machine, where the verdict panel silently fails. Change the URL in source when the service moves, and redeploy.
- `practiceSteps.ts` — The pure rules of the step-by-step exercise: `pressedPitches`, `stepStatus`, `noteName`, `stepProblem`, `handSelection`, `staffGray`, and the `PracticeStep`/`StepStatus`/`StepVerdict`/`VerdictsSnapshot`/`HandsSwitch`/`HandSelection`/`StaffGray` types. `stepProblem` is the ranking that turns RML's verdicts into the ONE word the strip shows — `wrong note`, then `chord jitter`, then `bad dynamics`, with `exit 2` above all of them and "no verdict yet" never written as `correct`. Waiting and checking carry **an empty text on purpose**: the strip expresses those two states with the dot (dim, or pulsing), and a placeholder sentence there would be noise. `handSelection` is the whole L/R switch model the user asked for on 2026-11-07 (each letter switches only its own hand; both lit = `both`, both off = pause, one-staff file = one switch): it says which letters get drawn, whether the session is paused and which hand to ask the service, and it is consulted by both `ScorePage` and `PracticeBar` so the two can never disagree on what the switches mean. `staffGray` answers the same request's second half — "when L or R are off the respective staff in the score becomes grey like the button" — with WHICH rendered staff groups dim: suffix `-1` (upper, right hand) and `-2` (lower, left hand) as OSMD ids them in the DOM; a one-staff file dims its only staff exactly when its only switch pauses; a file whose notes carry no staff numbers never dims, because there the switches change no exercise and a grey staff would lie. `ScorePage` keeps no opinion of its own about any of this. The word list is English because it is user-visible text (see `User Preferences` in `../../AGENTS.md`). It contains no threshold: it only orders verdicts the service already emitted. No React, no network, no `import.meta.env`, so it can be compiled and executed on its own. This is deliberate: it is the only place in the practice feature that decides anything, and it must stay testable without mounting a component or faking a service.
- `scoreMarks.ts` — The pure end-of-take plan: given the verdicts (RML ones, the two synthetic coverage rules `"never played"` / `"out of time"`, which arrive in the same map as ordinary rules with their own locations) plus the `correct` list and how many notes were played, it decides WHICH points get painted RED and which GREEN, WHAT the hover card says at each red, WHAT GRADE the take deserves, and WHEN the piece counts as ended — nothing else. `planMarks(verdicts, correct?)` returns `{columns, green, unpinned, broken}`: every rule that fell at the same point merges into ONE mark carrying one `MarkRule` per rule (a rule name plus, where the location carried one, the `{kind, played, written}` pair — never merged away, because two rules falling on one key are still two things to fix; `"out of time"` carries `{kind:"timing", played}`, so its line reads `you 500 ms late · score on time`); sorts by reading order; splits `exit 2` into a separate `broken` list that must never paint anything; keeps `unpinned` for violations that carry no point; and turns each `correct` spot (must carry an integer `attack`, or it is dropped — only `attack` drives the walk) into a `GreenSpot` **deduped against every red key and against itself**: red always wins an attack, a note never wears two colors, and green has NO tip — nothing registers a hover for it, by design. Rule keys pass through as names the service already made readable (`"out of time"`, `"never played"` are English sentences, not identifiers — the card prints rule keys raw). The metric is untouched by all this: the synthetics flow into `performanceScore` as ordinary exit-1 rules and the dedup key keeps each attack docking the grade once. `markLines(column)` writes the card's lines — one per rule, with `you D4 · score E4` for pitch pairs (formatted with `noteName`, imported from `practiceSteps.ts` so the keyboard and the card can never disagree on a key name) and `you 101 · score 84` for velocities; no pair, no detail — nothing invented. `markTipFor(column)` wraps those lines with `{measure, beat}` for the card header. `performanceScore(verdicts, noteCount)` is the 0–100 grade: flagged = distinct points of exit-1 rules (deduped by `attack`, else `measure:beat` — the same key `planMarks` uses, so one error never docks the grade twice just because two rules saw it) + one per violated rule with no point; `score = round(100 × (1 − flagged / max(noteCount, flagged, 1)))`; when NO monitor started (`judged === 0`) it returns `score: null` — "we don't know" is not 100. The denominator is the notes the performer played (`verdict.noteCount`), so the number is relative to this performance by construction and the page invents no threshold — side effect stated plainly: half a piece skipped now scores lower, because its untouched attacks are real misses, which is the honesty the user asked for. `summaryLines` writes the two or three English lines shown under the grade — where the red spots are, violations without a point, monitors that did not start; it refuses to say "every rule was respected" when something is unlocatable or broken. `endSignal(dur, pos, prevPos, pathMs, maxStepMs)` and `consumedFullTrack(dur, pathMs, maxStepMs)` answer WHEN the piece ended — rebuilt on 2026-11-10 after the user rejected the first fix ("potrebbero comunque capitare dei falsi positivi… preferirei qualcosa di più robusto che è sicuro al 100% che lo spartito è terminato"): `'top'` = `position ≥ duration − END_SLACK_MS` (2 ms; `position` IS `min(currentTime·1000, duration−1)` by the library's own definition, so it can only be at the ceiling once everything playable was played), `'rewind'` = position fell while the page's odometer `pathMs` (sum of positive position steps) shows the track consumed to within `WRAP_MARGIN_FACTOR` (2) measured max steps of `duration` — the margin is a multiple of the sampling step because that step is the only increment that can jump over the 2 ms window; it is never a percentage of the piece. A fall with the odometer mid-track is NOT the end (that was exactly the false positive feared). `consumedFullTrack` is exported alone because the page also asks it of the JUMP THE WORKLET DECLARES (`loopCount` drop, see pages doc): jump at a consumed track = the end the user complained was being replayed; jump mid-track = a written repeat, recording continues. Same purity contract as `practiceSteps.ts`: no React, no network, no `import.meta.env`, executed standalone by `alignment/run_scoremarks_tests.mjs` (**44** checks — which since 2026-11-10 must compile BOTH files into one output dir, because the shared `noteName` is a real import now). It never touches pitch itself: a point travels as `{measure, beat, attack}`, and only `attack` is fit to drive the walk (see Service contract in `../../AGENTS.md`).
- `usePractice.ts` — Transport and session state for the step-by-step mode. Calls `POST /practice` once (the plan) and `POST /practice/step` per step (the verdicts), and holds the cursor index, the last verdict, the local step status, and the hand being studied (`hand`, `hands`, `setHand`). Re-exports the `practiceSteps` types; it deliberately does NOT re-export the functions, so a test of the rules does not drag in React and the network.

## Local Contracts

- `useMidi` exports the `MidiNote`, `MidiEvent`, and `UseMidiReturn` interfaces; `useVerdict` imports `MidiEvent` from `useMidi` — the only cross-hook dependency left
- `useMidi.clearRecording()` empties `recording`, `events`, and `activeNotes`; `ScorePage` calls it when a take starts, so two consecutive takes do not concatenate into one payload
- `UseMidiReturn` carries TWO event streams, and they are not interchangeable: `events: MidiEvent[]` is a bounded live stream for the UI (cap 500, oldest dropped first), while `recording: MidiEvent[]` is the performance that gets analysed (cap 20000). A 216-note piece produces 434 events, so `events` alone silently loses the beginning of the performance
- `recording` must be read at analysis time, never subscribed to; `useVerdict` takes it as a plain argument and only reads it inside `analyse()`
- `useMidi` uses ref-tracked listener references so multiple instances don't clobber each other's global WebMidi listeners; never call bare `WebMidi.removeListener()` without a reference
- `useMidi` attaches the selected input's listeners and the ref-scoped global `connected`/`disconnected` handlers in an effect SETUP keyed on `isEnabled`, `selectedInput?.id`, and `attachListeners`, so delivery and hot-plug registration are re-established on every effect remount (Vite Fast Refresh / StrictMode) instead of being silently detached while the UI still shows the device as connected
- `useMidi.selectInput()` resolves the id before detaching: an empty or unresolvable id is a complete no-op — the live input keeps its listeners and the current selection is unchanged
- `useMidi.isSupported` is a lazy `useState` initializer (`!!navigator.requestMIDIAccess`), never a `setState` in an effect — do not reintroduce a support-check effect
- `useMidi`'s enable/disable global `connected`/`disconnected` handlers are typed `PortEvent` (the base `webmidi` event), not `MessageEvent`; `MessageEvent extends PortEvent`, so a handler typed `MessageEvent` is not assignable to the port-listener slot
- `enable()` surfaces `err instanceof Error ? err.message : ''` and then falls back to the default guidance string — an empty message must still produce the guidance, not `""` (pinned by `useMidi.test.ts`)
- Every string a hook hands to the screen is **English**: the `Error` texts thrown by `useVerdict`/`usePractice` (`the service responded with 502`, `The service found no steps to practise in this score.`, `Nothing was recorded: play the piece before asking for a verdict.`) land verbatim inside the red box of the page, so an Italian one here is a visible Italian even when every `.tsx` is clean. The strings coming back from the service follow the same rule and are documented in `../../AGENTS.md`
- `stepStatus` decides `advance` on set membership, never on time and never on a threshold: the expected pitches come from the service's plan, so this file invents no number
- `advance` ignores EXTRA pitches on purpose. A wrong note and an added note are the same verdict for `pitch-agreement` (one `noteon` with `pitchDist != 0`), but they must behave oppositely: the first blocks the cursor, the second must not. Measured against the real monitor in `alignment/test_practice.py`, case 6
- `usePractice.submit` advances the cursor immediately and asks the service for the verdict afterwards, in parallel. The verdict costs ~170 ms locally but ~2 s deployed (Render Free, 0.1 CPU), so a cursor that waited for it would freeze after every note
- `usePractice` one-shot-guards the verdict requests: an in-flight request absorbs later presses and the most recent state is judged, because out-of-order answers would show the verdict of a step the student already left
- A failed verdict request NEVER stops the exercise: it is surfaced on the strip ("no verdict from the service") and the session continues. Interrupting someone who is playing for a network problem is the worst thing this feature could do
- `exit 2` from the service means the monitor did not start (missing `swipl`, a spec that does not compile), NOT a violation. `stepProblem` ranks it above every playing problem and `PracticeBar` gives it its own tone (`.pb-broken`, violet); showing it as "wrong note" would tell the student they played badly when the service is broken. The same holds for end-of-take marks: `planMarks` keeps exit-2 rules out of every red note and names them in their own summary line
- `scoreMarks.planMarks` dedupes by `attack` when it exists (exact per construction — both sides read the same onset grid) and falls back to `measure:beat`; the walk order is chronological (`attack` ascending) because the OSMD cursor only moves forward, while reading order stays measure+beat. `performanceScore` counts its flagged points with that SAME dedup key — a rule pair falling on one attack is two lines in the hover card but ONE error on the grade, because the student fixes one keypress, not two
- The `{kind, played, written}` pair on a location is **raw integers** from the service (`_detail_for` in `../alignment/server.py`) and `scoreMarks.markLines` is the ONLY place that formats them into words (note names via `noteName`, plain digits for velocities). The page must pass the numbers through and never format: two formatters drift, and the drift would hide in the one sentence the student reads while fixing the note
- `usePractice.dynamicsOn` filters the DISPLAY, not the request: the four practice rules always run, and the flag only decides whether the word "bad dynamics" may appear on the strip. Filtering server-side would cost a round trip to switch a rule back on and would put a presentation choice into the judgement
- `usePractice.hand` is NOT like `dynamicsOn`: it changes the exercise. `setHand` re-requests `/practice`, because a hand-filtered plan has a different number of steps, asks different keys and points the cursor at other attacks; keeping the old list would judge the student on the hand they are not playing. `_probe_browser.mjs` asserts both halves: switching costs exactly one new plan request, and toggling dynamics costs none
- Every verdict request carries the hand the plan was built with, read from `handRef` and not from state — the callbacks are created once, so state would be stale. A mismatch is silent: step 5 of a left-hand plan would be judged against step 5 of the whole piece
- `stepStatus.other_hand` mirrors the service's `offhand`/`other_hand`: presses belonging to the excluded staff are declared and never counted as `extra`. Both sides must agree, or the counter and the verdict contradict each other on the same screen
- `reset()` clears the hand too: the hook itself must never know about persistence. Since 2026-11-10 `ScorePage` re-applies the user's persisted L/R switches on top of it through the existing plan-mapping effect, which costs **one extra plan request** when re-entering practice with a letter switched off — paid knowingly, because asking the service for the plan the switches actually describe beats keeping a wrong plan and filtering it locally. `hands` (what the file allows to split) comes back from the service with each plan and is what enables or disables the chips
- `noteName` uses the scientific convention: MIDI 60 = C4, 21 = A0, 108 = C8 (the 88-key range the RML specs cite). Accidentals are always sharps, because MIDI numbers do not distinguish them. It is what `PianoKeyboard` prints at the reference points and what `scoreMarks.markLines` puts into the hover card's "you D4 · score E4" — the same name in the picture and in the text, so the two cannot disagree (there are no tooltips left to use it in: the user deleted them on 2026-11-10)

## Work Guidance

- `useMidi.test.ts` runs on **bun**, not vitest (`bun test src/hooks/useMidi.test.ts`), because it drives `mock.module` for the module registry. `web-app/eslint.config.js` disables `react-hooks/globals`, `react-hooks/immutability` and `react-hooks/rules-of-hooks` for that file only: the harness runs the hook outside a React render tree, so those rules report its module-level state as violations. Its harness functions are named with a `use` prefix (`useRenderHook`, `useCreateHookWithInputs`) for that reason
- Keep new exercise rules in `practiceSteps.ts`, not in `usePractice.ts`: a pure module can be run by `alignment/run_practice_tests.mjs`, which does not depend on vitest starting. The same reasoning holds for the end-of-take marks: what they decide goes in `scoreMarks.ts` (run by `alignment/run_scoremarks_tests.mjs`), and `ScorePage` keeps only geometry — reaching the note and painting pixels is the page's job, deciding whether a rule deserves a red note is not
