# hooks — Domain-Logic Hooks

## Purpose

Stateful React hooks that encapsulate cross-cutting domain logic — MIDI device management, verdict transport, and the step-by-step practice session. Each hook owns a complex concern that would otherwise bloat page components.

## Ownership

- `useMidi.ts` — Web MIDI API integration via the `webmidi` package. Manages device enumeration, enable/disable lifecycle, input selection, live note-on/note-off tracking, two event streams, and hot-plug (connect/disconnect) events. Returns `UseMidiReturn` (the interface consumed by `MidiPanel` and `ScorePage`).
- `useVerdict.ts` — Carries a finished performance to the Cadenza service and holds the seven RML verdicts. `toPerformance(events)` is a pure function, exported for testing, converting the MIDI stream into the payload the service validates. It contains no threshold and no verdict: the verdict is computed in Prolog. `API_URL` defaults to the deployed service `https://cadenza-etji.onrender.com`; `VITE_CADENZA_API` overrides it for local development.
- The deployed URL is the default on purpose. It is a public address, not a secret, so hiding it behind an env var only created a way to forget it — and a forgotten env var points the app at the author's own machine, where the verdict panel silently fails. Change the URL in source when the service moves, and redeploy.
- `practiceSteps.ts` — The pure rules of the step-by-step exercise: `pressedPitches`, `stepStatus`, `noteName`, `stepProblem`, and the `PracticeStep`/`StepStatus`/`StepVerdict`/`VerdictsSnapshot` types. `stepProblem` is the ranking that turns RML's verdicts into the ONE word the strip shows — `wrong note`, then `chord jitter`, then `bad dynamics`, with `exit 2` above all of them and "no verdict yet" never written as `correct`. Waiting and checking carry **an empty text on purpose**: the strip expresses those two states with the dot (dim, or pulsing), and a placeholder sentence there would be noise. The word list is English because it is user-visible text (see `User Preferences` in `../../AGENTS.md`). It contains no threshold: it only orders verdicts the service already emitted. No React, no network, no `import.meta.env`, so it can be compiled and executed on its own. This is deliberate: it is the only place in the practice feature that decides anything, and it must stay testable without mounting a component or faking a service.
- `usePractice.ts` — Transport and session state for the step-by-step mode. Calls `POST /practice` once (the plan) and `POST /practice/step` per step (the verdicts), and holds the cursor index, the last verdict, the local step status, and the hand being studied (`hand`, `hands`, `setHand`). Re-exports the `practiceSteps` types; it deliberately does NOT re-export the functions, so a test of the rules does not drag in React and the network.

## Local Contracts

- `useMidi` exports the `MidiNote`, `MidiEvent`, and `UseMidiReturn` interfaces; `useVerdict` imports `MidiEvent` from `useMidi` — the only cross-hook dependency left
- `useMidi.clearRecording()` empties `recording`, `events`, and `activeNotes`; `ScorePage` calls it when a take starts, so two consecutive takes do not concatenate into one payload
- `UseMidiReturn` carries TWO event streams, and they are not interchangeable: `events: MidiEvent[]` is a bounded live stream for the UI (cap 500, oldest dropped first), while `recording: MidiEvent[]` is the performance that gets analysed (cap 20000). A 216-note piece produces 434 events, so `events` alone silently loses the beginning of the performance
- `recording` must be read at analysis time, never subscribed to; `useVerdict` takes it as a plain argument and only reads it inside `analyse()`
- `useMidi` uses ref-tracked listener references so multiple instances don't clobber each other's global WebMidi listeners; never call bare `WebMidi.removeListener()` without a reference
- `useMidi` attaches the selected input's listeners and the ref-scoped global `connected`/`disconnected` handlers in an effect SETUP keyed on `isEnabled`, `selectedInput?.id`, and `attachListeners`, so delivery and hot-plug registration are re-established on every effect remount (Vite Fast Refresh / StrictMode) instead of being silently detached while the UI still shows the device as connected
- `useMidi.selectInput()` resolves the id before detaching: an empty or unresolvable id is a complete no-op — the live input keeps its listeners and the current selection is unchanged
- `useMidi.isSupported` is a lazy `useState` initializer (`!!navigator.requestMIDIAccess`), never a `setState` in an effect — do not reintroduce a support-check effect
- `useMidi`'s enable/disable global `connected`/`disconnected` handlers are typed `PortEvent` (the base `webmidi` event), not `MessageEvent`; `MessageEvent extends PortEvent`, so a handler typed `MessageEvent` is not assignable to the port-listener slot
- `enable()` surfaces `err instanceof Error ? err.message : ''` and then falls back to the default guidance string — an empty message must still produce the guidance, not `""` (pinned by `useMidi.test.ts`)
- Every string a hook hands to the screen is **English**: the `Error` texts thrown by `useVerdict`/`usePractice` (`the service responded with 502`, `The service found no steps to practise in this score.`, `Nothing was recorded: play the piece before asking for a verdict.`) land verbatim inside the red box of the page, so an Italian one here is a visible Italian even when every `.tsx` is clean. The strings coming back from the service follow the same rule and are documented in `../../AGENTS.md`
- `stepStatus` decides `advance` on set membership, never on time and never on a threshold: the expected pitches come from the service's plan, so this file invents no number
- `advance` ignores EXTRA pitches on purpose. A wrong note and an added note are the same verdict for `pitch-agreement` (one `noteon` with `pitchDist != 0`), but they must behave oppositely: the first blocks the cursor, the second must not. Measured against the real monitor in `alignment/test_practice.py`, case 6
- `usePractice.submit` advances the cursor immediately and asks the service for the verdict afterwards, in parallel. The verdict costs ~170 ms locally but ~2 s deployed (Render Free, 0.1 CPU), so a cursor that waited for it would freeze after every note
- `usePractice` one-shot-guards the verdict requests: an in-flight request absorbs later presses and the most recent state is judged, because out-of-order answers would show the verdict of a step the student already left
- A failed verdict request NEVER stops the exercise: it is surfaced on the strip ("no verdict from the service") and the session continues. Interrupting someone who is playing for a network problem is the worst thing this feature could do
- `exit 2` from the service means the monitor did not start (missing `swipl`, a spec that does not compile), NOT a violation. `stepProblem` ranks it above every playing problem and `PracticeBar` gives it its own tone (`.pb-broken`, violet); showing it as "wrong note" would tell the student they played badly when the service is broken
- `usePractice.dynamicsOn` filters the DISPLAY, not the request: the four practice rules always run, and the flag only decides whether the word "bad dynamics" may appear on the strip. Filtering server-side would cost a round trip to switch a rule back on and would put a presentation choice into the judgement
- `usePractice.hand` is NOT like `dynamicsOn`: it changes the exercise. `setHand` re-requests `/practice`, because a hand-filtered plan has a different number of steps, asks different keys and points the cursor at other attacks; keeping the old list would judge the student on the hand they are not playing. `_probe_browser.mjs` asserts both halves: switching costs exactly one new plan request, and toggling dynamics costs none
- Every verdict request carries the hand the plan was built with, read from `handRef` and not from state — the callbacks are created once, so state would be stale. A mismatch is silent: step 5 of a left-hand plan would be judged against step 5 of the whole piece
- `stepStatus.other_hand` mirrors the service's `offhand`/`other_hand`: presses belonging to the excluded staff are declared and never counted as `extra`. Both sides must agree, or the counter and the verdict contradict each other on the same screen
- `reset()` clears the hand too: re-entering practice must find the whole piece, not last session's left hand. `hands` (what the file allows to split) comes back from the service with each plan and is what enables or disables the chips
- `noteName` uses the scientific convention: MIDI 60 = C4, 21 = A0, 108 = C8 (the 88-key range the RML specs cite). Accidentals are always sharps, because MIDI numbers do not distinguish them. It is what `PianoKeyboard` prints at the reference points and what the toggle's tooltip uses — the same name in the picture and in the text, so the two cannot disagree

## Work Guidance

- `useMidi.test.ts` runs on **bun**, not vitest (`bun test src/hooks/useMidi.test.ts`), because it drives `mock.module` for the module registry. `web-app/eslint.config.js` disables `react-hooks/globals`, `react-hooks/immutability` and `react-hooks/rules-of-hooks` for that file only: the harness runs the hook outside a React render tree, so those rules report its module-level state as violations. Its harness functions are named with a `use` prefix (`useRenderHook`, `useCreateHookWithInputs`) for that reason
- Keep new exercise rules in `practiceSteps.ts`, not in `usePractice.ts`: a pure module can be run by `alignment/run_practice_tests.mjs`, which does not depend on vitest starting

## Verification

- `npm run lint` — ESLint (note: `ScorePage` disables `react-hooks/exhaustive-deps` on specific effects)
- `npm run build` — TypeScript type-check
- `npm test` — vitest (`usePractice.test.ts` covers the pure rules, the excluded-hand cases and the `stepProblem` ranking). **Does not cover `useMidi.test.ts`** (excluded in `vite.config.ts`). Run `bun test src/hooks/useMidi.test.ts` (21 tests) as the gate for this directory
- `node alignment/run_practice_tests.mjs` — compiles `practiceSteps.ts` with tsc and executes it on node, 33 checks: completeness, the excluded-hand split, and the ranking of the compact verdict line. The fallback that works when vitest cannot start (Vite calls `execFile`, which a sandboxed environment denies), and it runs the same emitted module the bundle uses
- `python alignment/test_cursor.py` — 21 checks on the cursor-walk logic, with an OSMD stand-in (`Iterator.EndReached`, `Iterator.CurrentMeasure.MeasureNumber`, `next`, `reset`, `show`, `hide`). It tests OUR function, not OSMD: it cannot catch an OSMD API change, which is what the browser check is for
- `python alignment/test_cursor_sequence.py` — the real 128-step sequence against a cursor built from the real score. It asserts 128/128 steps positioned, 128/128 on the right measure, 128/128 cursor movements, zero backward walks. The voices are deliberately shifted by 36 semitones, like OSMD does: if the function depended on pitch, this test would fail
- `python alignment/test_practice.py` / `python alignment/test_server.py` — the service side of the same split (13 cases on the plan and the hand filter, 30 HTTP contract checks including `hand`, `hands`, `attack` and `other_hand`). The two halves must keep agreeing: run both after changing `practiceSteps.ts`
- Manual: connect a MIDI keyboard, press "Play along", play the whole score, and check that the verdict arrives by itself. Then press "Practice" and check that the drawn keyboard lights exactly the keys of the current step and turns green under the fingers, that the exercise advances only when every asked key has been pressed, that the OSMD cursor moves to the note of the current step, that the **D** chip's tooltip states what is no longer watched when off, and that **L** / **R** change which keys are asked (and, for the left hand, how many steps there are) while both staves stay on screen
