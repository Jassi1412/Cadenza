# components — Reusable Presentational Components

## Purpose

Stateless and lightly-stateful UI components reused across pages. Each component is paired with a co-located `.css` file and is consumed by one or more page components.

## Ownership

- `MidiPanel.tsx` / `.css` — Collapsible MIDI connection panel. Renders device selector, live note display, mini keyboard visualization (C3–B4). Consumes `UseMidiReturn` from `useMidi`. Returns `null` on unsupported browsers.
- `PlaybackBar.tsx` / `.css` — Floating bottom control bar. Exposes **Playback**/Pause (listen only), Stop, **Play along** (starts a recorded take), and **Practice** (step-by-step). Every word is English; the words ON the buttons are their labels — the explanatory `title` tooltips are gone since 2026-11-10 (user preference: no native tooltips on anything the musician touches, see `../../AGENTS.md`). Also owns the tempo slider (the one control that keeps an `aria-label`, having no word of its own). Renders a thin progress line (0–100%), hidden during a take and during practice. Uses Material Symbols icons + a custom stopwatch SVG for the play-along button. Solid background: see the `PracticeBar` bullet.
- `PracticeBar.tsx` / `.css` — The one-row practice command strip, fixed above `PlaybackBar`: the verdict dot + word, the keyboard toggle (**a `Piano` lucide icon**, `#bar-keys-btn`), the two hand buttons **L** / **R** and the dynamics chip **D**. Presentational — it decides nothing and never calls the service: the verdict text arrives already chosen by `stepProblem`, the completeness by `stepStatus`. It replaced `PracticePanel.tsx` / `.css` (the box that covered half the score) — do not reintroduce that box. No native tooltips on any of its controls (2026-11-10): the strip shows only what is glanceable while the eyes are on the keys, and what is not shown is **gone on purpose**, not parked in a hover rectangle. It also no longer prints counters: a step number never told the student *which* key to press, and the gold keys say that directly.
- `PerformanceCard.tsx` / `.css` — The end-of-take card: centered in the viewport (not docked under the score, not a scroll target), status machine `working → error | done`. `done` shows the 0–100 grade counting up from 0 over ~1.1 s (`useCountUp`, rAF ease-out cubic; under `prefers-reduced-motion` the first animation frame already carries the final number — motion never holds the information), colored by band (≥85 green, ≥50 gold, <50 red — the same palette as keyboard and strip) plus `summaryLines`' English lines underneath; `score === null` renders "Nothing could be judged" in violet instead of a fake 100. The number itself comes from `performanceScore`; the card displays it, it never computes. Props in (`status`, `error`, `outcome`, `lines`, `onClose`, `onPlayAgain`), buttons reuse `.btn-primary`/`.btn-outline`.
- `ErrorHoverCard.tsx` / `.css` — What a red note means: one line per rule that fell on it, each with the pressed-vs-written pair where the service carried one (`you D4 · score E4`), and `measure N · beat B` in the header. Lines come from `markTipFor`; the card adds only geometry — it positions itself by writing `left`/`top` **on the node inside a layout effect** (no state round trip: two css numbers do not deserve a re-render, and the repo's no-setState-in-effect rule says so in as many words), flipping left/up near the viewport edges because a card half off-screen is worse than none. `pointer-events: none` — it appears under the cursor without stealing the hover that produced it.
- `PianoKeyboard.tsx` / `.css` — The drawn hint keyboard that appears above the strip while practising: plain DOM rectangles, no library and no canvas. Always the **whole instrument — all 88 keys, A0 (21) to C8 (108)**, the same endpoints the RML specs cite; the user asked for every key on 2026-11-05 because a cropped keyboard never says where the piece sits on the instrument, which is the one thing a pianist orients by. `PIANO_LOW` / `PIANO_HIGH` are exported and are the default `low`/`high` props (a caller may narrow them — tests, very narrow screens — but never for convenience). Props in (`expected`, `pressed`, `extra`, `offhand`), nothing decided, nothing sent. Middle C carries a dot; reference names are printed at the C's and F's; the step's keys are gold, correctly pressed ones green, unasked presses red, the other staff's notes violet. A black key that is in one of those four stories gets its name written on it (`pk-tag`) — on a full keyboard an unnamed lit sharp is just a dark smudge.
- `StaffToggle.tsx` / `.css` — REMOVED with the old note-by-note practice engine. It existed only to pick which staff that engine waited on, and the play-along mode records the whole keyboard, so there was nothing left to toggle.

## Local Contracts

- Components receive all data and callbacks via props — no direct hook usage inside presentational components except local UI state (e.g. `MidiPanel` expand/collapse)
- Each component imports its own `.css` file; styles are scoped by component-specific class names
- `MidiPanel` depends on the `UseMidiReturn` interface exported from `hooks/useMidi`
- `PlaybackBar` is controlled — `ScorePage` owns playback state and passes `isTakeActive`, which disables Playback/Pause during a take and relabels **Play along** to "Recording" (the presses are captured from the countdown on, so the label states what is actually happening)
- `PlaybackBar` is controlled in practice too: `isPractice` hides the progress line and the tempo slider, disables Playback and Play along, and makes **Practice** read "Exit". The tempo slider disappears rather than being disabled, because in the step mode no duration matters and a slider that looks adjustable while meaning nothing is worse than no slider
- The lit keys on `PianoKeyboard` follow the LOCAL step status (`status.pressed` / `status.extra`), never the server verdict. The verdict costs ~2 s deployed; if the colours waited for it, the finger would already be on another key before the screen caught up
- The verdict line has THREE tones, not two: `.pb-ok` (`correct`), `.pb-warn` (what the student played: `wrong note` / `chord jitter` / `bad dynamics`) and `.pb-broken` (service `exit 2`, the monitor did not start). Collapsing broken into warn reports a broken service as bad playing. `.pb-waiting` is the fourth honest state: no verdict yet, or nothing pressed — and it shows **no word**, just the dot, which pulses while a request is in flight (`@keyframes pb-breath`). A silence that reads as `correct` is the one lie this project refuses
- The ranking lives in `stepProblem` (`hooks/practiceSteps.ts`), not here: `wrong note` before `chord jitter` before `bad dynamics`, and `exit 2` above all of them. The component renders the word it is given; that is what makes the ranking testable
- The suspended rules lost their on-screen home when the tooltips did (2026-11-10): practice mode runs four of the seven rules and always suspends three, and nothing in the strip or the keyboard says which. That loss was chosen — the user would rather see nothing than a grey rectangle — but if those rules ever need to be visible again, the place is the drawn UI (a dimmed legend, the card), never a `title`
- `PracticeBar` is ONE row, 2.4 rem tall (≈38 px), `position: fixed` at `bottom: calc(1.5rem + 5rem + 0.6rem)` so it sits directly above the pill, sharing its width (`max-width: 34rem`) and radius. It must not grow into a panel: the box it replaced measured 207 px closed and 471 px open, and it covered half of the score — while the thing to look at, the cursor, is on the score
- Both bars are **solid** `--bg-secondary`, no `backdrop-filter`, alpha 1. They float over the rendered score, and as 0.85-alpha glass the notes showed through the controls, which is what made the buttons hard to read; an opacity check now belongs to the browser probe. The two bars share one colour, so their border (`rgba(197,168,128,.35)`) is the only thing separating them — never make one transparent and leave the other opaque
- `PianoKeyboard` is fixed above the strip (its own `bottom` = the pill's offset + the strip's height + a gap), `width: 98%` capped at `max-width: 76rem` — deliberately about twice the strip's 34 rem, because 52 white keys in a narrower box turn into stripes and stop being keys (at 76 rem a white key is ~23 px). `z-index: 999` — one below both bars, which stay readable — and `pointer-events: none`: it is a picture to glance at, not a control, and the keys you press are on the real instrument under your hands. Being above the strip is not cosmetic: a keyboard below or beside the controls hides the verdict word
- The overlay stack is fixed arithmetic, not taste: strip and pill at 999/1000, `PerformanceCard` layer at **1001**, `ErrorHoverCard` at **1002** — a hover card that lands *under* the grade card while both are up tells the student the wrong thing about the note they are reading. The card layer covers the viewport but has **no dark veil**: `pointer-events: none` on the layer, `auto` only on the card itself — the red marks stay visible around it, because the card is there to explain them, not to hide them. Both cards wear the existing skin (`--bg-secondary`, gold hairline, the same band colors): a new visual language for two small boxes would be the fifth meaning this feature's palette refuses
- One colour language across the whole feature: gold = what to press, green = pressed correctly, red = played but not asked for, violet = the other staff / not your fault. The keyboard reuses exactly the palette of the `.pb-*` tones and the cursor on purpose; a fifth meaning would split the language
- Names are printed only at the C's and F's, plus a dot on middle C. Printing all twelve names per octave over 52 white keys is a wall of text and stops being glanceable: the point of the keyboard is *where*, not a transcription. The labels degrade by media query — under 68 rem the F's go (the C's alone still orient), under 34 rem every label goes and only colour + the black-key `pk-tag` carry meaning
- The hand control is **two independent switches** — **L** / **R**, drawn from `hands.right > 0` and `hands.left > 0` (a staff with no notes gets no letter at all). Since 2026-11-07 each click turns **only its own hand** on or off: lit = that hand takes part, off = its staff is not asked for, does not stop the cursor and is not judged; **both lit is the whole piece** (the user deleted the third "all" chip earlier and two lit letters still say it), **both off is a deliberate pause**: the strip shows its own grey line — `Both hands are switched off — press L or R to continue` — with **no pulsing dot**, because nothing is in flight and a pulsing dot would lie. Which letters get drawn, whether it is a pause and which hand to query are decided by `handSelection` in `hooks/practiceSteps.ts`, consulted identically by this strip and by `ScorePage`: one formula, two readers, no way to diverge
- The off letter carries `.pb-chip-off` — grey on grey, like an unlit bulb, so the exclusion reads at a glance while the eye is on the keys — but it stays **clickable**: a switch that looks disabled cannot switch itself back on. These chips are never `disabled` (`run_practice_tests.mjs` pins the table; `_probe_browser.mjs` compares the two computed colours to prove the difference is visible, not just a class)
- When a file carries notes on one staff only, exactly ONE letter is drawn: the absent hand has no notes to offer, and drawing it would promise an exercise with no notes in it. That one letter is still a real switch: turning it off pauses the session, and its line names the staff — "The right staff is switched off — press R to continue" — which is also the whole reason, so nothing else hides behind the mouse
- Choosing a hand does not hide any staff. Both staves stay visible: the filter changes what is judged and what advances the cursor, and the excluded staff is still the ground the cursor walks on. Re-planning is `usePractice.setHand`, never this component
- Presses belonging to the excluded staff are shown as violet keys (`pk-offhand`) and declared there, on the drawn keyboard — never counted as extra and never red: they were asked for, just not by this hand. With no tooltips left, those violet keys ARE the declaration
- The **D** chip (`aria-label="Dynamics"`) filters the DISPLAY only (`aria-pressed`). It must never cost a round trip — the service always runs all four practice rules — and `_probe_browser.mjs` asserts that by counting requests, and asserts its `title` stays absent after a toggle (the tooltip must not creep back with the state)
- Single-letter chips (L / R / D) carry `aria-label`s in full; a screen reader must not read three letters. Letters are allowed on the chip face because they sit beside two other icon controls and the icons already say what kind of control it is — unlike the three mode buttons, whose words are their labels
- `PracticeBar` must not export helper functions: `react-refresh/only-export-components` rejects it. `noteName` and `stepProblem` therefore live in `hooks/practiceSteps.ts`, where they are also testable

## Work Guidance

- Use `lucide-react` for standard icons; use inline SVG only when no suitable lucide icon exists (see the `PlaybackBar` stopwatch). The practice strip's keyboard toggle uses the lucide `Piano` glyph, the same icon `MidiPanel` already ships with; the step button uses Material Symbols (`piano` / `close`) to match the icons beside it
- Material Symbols icons are loaded via class `material-symbols-outlined` with `fontVariationSettings` for weight/fill control
- New components must follow the same pattern: `React.FC<Props>`, named export, co-located CSS, component-scoped class names

## Verification

- `npm run lint` — ESLint with React Hooks + React Refresh plugins
- `npm run build` — TypeScript type-check + Vite build
- `node ../alignment/_probe_browser.mjs` (dev server on 5173 + a Cadenza service; origin must match between `VITE_CADENZA_API` and `PROBE_API`, see `../pages/AGENTS.md`) — **90** checks in a real browser, the components-owned ones among them: both bars compute an alpha of 1, the strip stays under 70 px and above the pill with the keyboard above the strip, the keyboard draws exactly **52 white + 36 black keys from pitch 21 to 108**, every pitch the first step asks or declares is actually drawn (this check exists because a windowed first version silently omitted A5 — swapped `min`/`max` variables, invisible to `tsc`), an asked black key carries its correct `pk-tag`, the keys it lights are the ones the plan asked for, **no control on the strip carries a native `title`** (on every one of `#bar-keys-btn` / `#bar-hand-left` / `#bar-hand-right` / `#bar-dyn-btn`, before and after toggling D — while every one of them keeps its `aria-label`, which is what makes removing tooltips safe), **D** costs no request, and leaving practice takes the keyboard away; and since 2026-11-10 it closes a real take end to end as well — the grade card is verified centered on the viewport (within 108/135 px of 720/450, measured live), "Close" takes the card away AND the red marks stay painted on the score for reading (the probe counts them right after the click; see "Two colors, one per attack" in `../pages/AGENTS.md`)
